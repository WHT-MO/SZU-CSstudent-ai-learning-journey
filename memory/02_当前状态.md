## 易错点与教学边界

- `{ "messages" }` 是 set；`{"messages": []}` 是 dict。`len(state)` 数键，`len(state["messages"])` 数消息。日志存可变字典引用会随之后状态变化；消息数快照应存当时的整数。
- `create_task` 后尚未等待任务完成；完成回调必须接收 Task 参数。`task.exception()` 读取失败结果；Task 不能手动 `set_result`，Future 可以。
- 一条教学消息只推一个新概念；前置不懂就先讲，练习代码由学员自己写。只有实际引入新库时才说明导入/安装，不重复提示“无需新库”。不提前泄露检查题答案。
- 学员要求代码审查同时看命名与可读性；参数与字段优先使用清晰、常见、便于工程协作的英文名，避免中文拼音式命名。**下一课要求学员自己保证项目代码的可读性，教员只指出具体问题与原因，不代改或在“归档”时悄悄改描述、结构、打印行为。** 2026-09-24 收尾时教员把草稿迁入项目却改了三份描述、格式和打印入口，学员指出不一致；现已恢复草稿原文，待学员下次亲自整理。当前工具说明书的 `name`、`description`、`parameters`、`path`、`content` 均符合命名口径。
- 对新方法和工具采用“够用理解”标准：先知道它解决什么问题、输入和输出、是否改变数据、一个常见失败点，再进入项目；不要求背实现细节。`httpx.post`、`os.getenv`、`list.pop` 等出现时必须先放回 Agent 架构地图，避免只记调用格式。
