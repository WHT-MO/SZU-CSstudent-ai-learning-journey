## 0. 一句话目标（2026-09-23 学员更正）

> **首要目标：掌握 Agent 开发技术栈。** 同时完成一个能运行的命令行演示、整理成可公开展示的 GitHub 项目，并能清楚讲解设计与故障处理。
> **运行成功是第一道门槛，能解释为什么这样设计才算学会。**

→ **目标函数因此改写**（这是本次最重要的更正）：

| | 旧口径（已作废） | **新口径** |
|---|---|---|
| 优化对象 | 工具的**可用性与鲁棒性** | **理解深度 + 可展示的证据** |
| 代码行数 | 1200–1800 行是目标 | 行数只是**副产品**，不是指标 |
| 验收 | "连续 5 天没有一天因为它出错而改回手做" | **每个模块你能讲出"为什么必须有它、没有它会怎样"**，且有自己的证据 |
| 砍功能的理由 | "功能少 = 你敢用" | "这个功能**教不到东西**，才砍" |

**"天天用"降级为加分项，不再是验收线**：仍然要能跑通、要真的用它干过活（不然是空的），
但**不追求"每天都靠得住"**——那会吃掉大量时间在边缘 case 上，而那些 case 教不到 agent 原理。

### v1 的验收标准（三条，缺一不可）

1. **结构能画**：不看资料，凭记忆画出 agent 的数据流与模块结构（你有这个强项——L17 复习课第一版就画到六到七成）。
2. **机制能讲**：每个模块用"12 岁能听懂"的话讲一遍，并指出**它解决什么、不解决什么**。
3. **坑能复现**：能**主动造出**下面这些故障并解释你怎么发现的、怎么修的（**每条的造法与前置条件见 §5.4，不许等它自然发生**）：
   - 工具调用死循环（用 `maxTurns` / `maxUnboundToolCalls` 兜住）
   - `reasoning_content` 漏传 → 在当前协议要求下返回 400（**前置：必须开 thinking**）
   - 后台 asyncio 任务可能被回收（Python 3.12 弱引用；主动 `gc.collect()` 并如实记录本机表现）
   - 429 与指数退避（**用假 429 响应，不等真实限流**；含"哪些错误**不该**重试"）
   - 上下文被压缩前后，**发给模型的 messages 真的变小了**（不是只追加了一条记录）

> **判据一句话：能不能拿它去面试讲 20 分钟，且面试官追问"为什么这么设计"你能答。**

## 1. 砍掉清单（**判据已更正：不是"用不上"，而是"教不到东西"**）

| 砍掉 | 理由（2026-09-23 更正后） |

| 子 Agent / Skills / 扩展**加载机制** | 要看懂"机制"，**不需要自己实现一套**——见 §9「读什么、不读什么」 |

> 这些是 12 周培训班不教、只有从零写一遍才会懂的东西。
> **简历的含金量来自"把难的地方钻透"，不是来自功能清单的长度。**

### 2.2 项目边界与开工清单

- **项目目录**：`code/agent_v1/`；项目代码、项目专属 `README.md`、依赖清单和 `.env.example` 都放这里。复用仓库根目录已验证可用的 `.venv`，先在仓库根目录激活环境，再进入项目目录运行命令。
- **一句话需求 / MVP**：在命令行里用自然语言让 DeepSeek Agent 读取、列出、创建或精确修改 `workspace/` 内的个人文件；不联网搜索、不触碰工作区外路径、不做 GUI。
- **模块与数据流**：CLI → Agent Loop/会话状态 → DeepSeek API；模型返回工具调用时，由 Tool Registry 校验并执行四个文件工具，再把工具结果回传模型，直到回答或触发停止条件。事件顺序固定为先更新 state、再按注册顺序通知 listener。
- **存储**：`.env` 放本机密钥；JSONL 保存 append-only 会话；`ledger.jsonl` 记每次调用的 token 与费用估算；`workspace/` 放 Agent 可操作文件。README 记录入口、模块图、数据流和复现步骤。
- **Agent 可操作的文件根目录**：`code/agent_v1/workspace/`。四个文件工具只能读写这里；拒绝绝对路径、`..` 越界和解析后落到根目录外的符号链接。
- **四个工具固定为**：`list_files`、`read_file`、`write_file`、`edit_file`。`edit_file` 只在旧文本恰好出现一次时修改；零次或多次匹配都报清楚错误且不改文件。
- **首个演示命令**：先在 `workspace/README.md` 放入无敏感信息的短样例；在仓库根目录激活 `.venv` 后进入 `code/agent_v1/`，运行 `python agent.py --once "读一下 workspace/README.md 第一行"`。仓库课程总 README 与 Agent 的可操作工作区分开。
- **项目 README 必须能让别人从零跑起来**：Python 版本、建环境/装依赖、配置 API、运行命令、架构与数据流图、验证步骤、费用/能力边界。
- **公开展示边界**：完成后把 `code/agent_v1/` 整理成独立展示仓库，只带项目代码、必要文档、依赖清单和无密钥样例；发布前检查文件与提交历史中的个人信息、真实密钥和日志。课程仓库的 `memory/02_当前状态.md` 曾包含较长的个人学习记录；只缩短现行文件不会移除旧 Git 历史，因此不要直接把整个课程仓库当作 Agent 展示项目。
- **密钥**：本机 `.env` 保存 `DEEPSEEK_API_KEY`；提交 `.env.example`（仅占位符），不得把真实密钥写进聊天、截图、日志或 Git。仓库根 `.gitignore` 必须忽略 `.env` 和其他 `.env.*`，同时保留 `.env.example`。**预算按人民币 ¥100 理解**；每次请求记录用量和估算费用，达到上限即停止付费请求。
- **模型选择**：本机约 8 GiB 显存和 31.8 GiB 内存，不适合部署完整 DeepSeek V4.1 Flash（官方模型卡标为 763B 参数）。v1 主路径走 DeepSeek API；本地小模型作为 v1 之后的独立实验，不阻塞 Agent 主线。模型名和价格以实现当天的[官方文档](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)为准；当前文档列出的 V4.1 Flash API 名称为 `deepseek-flash`。

**开工前环境门禁（先做一次，不算重复建环境）**：

1. **复用仓库根目录 `.venv`**：2026-09-24 已在用户 PowerShell 验证它的解释器路径位于 `.venv\Scripts\python.exe` 且 `sys.prefix != sys.base_prefix` 为 `True`。不再创建第二个 venv。
2. 从仓库根目录运行 `& .\.venv\Scripts\python.exe -m pip --version` 和 `& .\.venv\Scripts\python.exe -m pip show httpx pydantic python-dotenv`。项目 `requirements.txt` 记录这三项；若缺失，再通过这个解释器安装该文件里的依赖。
3. 日常使用时，在仓库根目录激活 `.venv`，再进入 `code/agent_v1/`；用 `python -c "import sys; print(sys.executable); print(sys.prefix != sys.base_prefix)"` 和 `python -m pip --version` 确认。仅看到提示符有 `(.venv)` 或 `Get-Command python` 有结果不算验收。
4. 若用户 PowerShell 中直接运行仓库 `.venv` 再次提示 `No Python at ...WindowsApps...python.exe`，先不要卸载 Python或覆盖环境；先创建临时 venv 对照，再决定是否按[官方 Windows 安装说明](https://docs.python.org/3/using/windows.html)安装 Python Install Manager/官方 CPython。不要把 `deactivate` 报错当成 Python 损坏：提示符没有 `(.venv)` 时本来就未激活，无需执行 `deactivate`。
5. 若 PowerShell 阻止激活脚本，只在当前窗口执行 `Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned`，再激活；这项设置关闭窗口后失效。

## 3. 三个阶段门禁（按交付验收，不按日期卡人）

| 阶段门禁 | 判据 | 不达标怎么办 |
|---|---|---|
| **基础机制门禁（W1 三格）** | 异步对照清楚；后台任务异常可见，GC 场景记录无强引用/强引用对照结果；两个 listener 都看到更新后的 state。此阶段不要求模型/API 请求 | 缩小例子直到异步、异常处理和事件顺序可验证；GC 结果按本机实际记录，真模型请求仍留在工具协议之后 |
| **首个闭环门禁（W2 第 6 格）** | **真请求能完成一轮工具调用闭环**（非流式即可） | 降级为假模型先走完同一条数据流，再用一条短 API 请求单独确认连接；限流、压缩等机制继续做可控本地复现 |
| **会话恢复门禁（W3 第 8 格）** | 会话能存、能恢复；在当前官方协议要求时，**开启 thinking 后**第二次继续不因漏传 `reasoning_content` 失败 | 若 API 接入暂时不通，JSONL 和恢复仍用固定响应做机制练习；故障档案记录 API 的真实状态与文档版本，不伪造 400 |

> **检查点口径修正（2026-09-24）**：① 阶段门禁绑定交付物，不绑定必须等到的日期；② 基础异步/任务/事件阶段不提前要求模型/API 请求；③ 流式输出仍是选做；④ 漏传 `reasoning_content` 是否返回 400 以实现当天的官方协议为准，默认关闭 thinking 时不会复现该条件（见 §5.4）。

> **门禁不达标时先缩小交付范围**，用固定响应或假传输学清机制；API 当天不可用不应阻止本地的协议、状态与错误处理练习。

> **完成前三格后现场数一次真账**（不许估）：实际用了几格、每格多久、卡点集中在哪。把实测用时用于余下进度估算；本文的 W1–W5 是主题阶段和保守日期，不要求按周等候。

> **开工前同步一次学习状态**：按协议，以 `memory/02_当前状态.md` 为进度权威来源。第 1 格开始前，核对它已包含本计划、当前目标、时间安排和环境门禁状态；缺哪项补哪项。实际计时从第一格开始，不沿用旧日期估算。

## 5. 三个机制坑、一个顺序约定与五类故障的主动造法

> **本节分工**：下面三个坑是**机制**（为什么会坏），坑 3 是 W1 的事件顺序约定；§5.4 列出五种需要留档的故障及可控造法。
> **原则（2026-09-23 review 指出）：五条故障档案一条都不许靠"等它自然发生"**——那样五周内大概率一条都集不齐。

### 坑 1：`reasoning_content` 必须全程回传（**v1 最致命的一个**）

官方 Thinking Mode 文档原文：只要请求带 `tools` 参数，**所有历史轮次的 `reasoning_content` 都必须完整传回 API，否则直接返回 400**——即使某一轮模型没有调用工具也一样。

→ 影响：**W3 的会话存档如果不存 `reasoning_content`，会话第二次继续就永久 400**，而且报错信息不会告诉你原因。
→ 做法：存档时 assistant 消息必须同时写 `content` + `reasoning_content` + `tool_calls` 三个字段。
→ **前置条件：必须开 thinking**——详见 §5.4 第 1 条。默认 `off` 时永远复现不出来。

### 坑 2：Python 3.12 的 asyncio 任务**可能**在未完成时被回收

Python 官方文档的措辞是**"可能"（may）**：事件循环对 `asyncio.create_task()` 创建的任务只持有弱引用，没有外部强引用的任务**可能**在 `await` I/O 时被垃圾回收。错误未必会传到主流程；也可能出现 `Task was destroyed but it is pending!` 警告。本机 2026-09-24 的 Python 3.12.10 受控实验出现了这条警告，不能把“静默”或“必然回收”当作通用结论。

→ 做法：维护一个全局任务注册表（`set()`），创建时 `add`，`done_callback` 里 `discard`；后台任务必须保留返回值并挂异常回调。
→ **不要靠"碰巧被回收"来验证**——用 `gc.collect()` 主动触发，见 §5.4 第 2 条。

### 坑 3：`emit()` 顺序必须在 W1 定死

**先归约内部 state（含 assistant message 的 `tool_calls` 提取），再按注册顺序 `await` listener。**

→ 如果顺序反了，listener 读到的是**更新前的 state**；等到 W3 加持久化时，存进去的就是旧数据——**这个顺序 W1 不定，W3 必返工**。

### §5.4 五条故障档案：前置条件、造法和证据

| 故障 | 可控造法 | 通过证据 / 边界 |
|---|---|---|
| 工具调用循环不停止 | 用固定假模型跑两个场景：反复请求一个合法工具，验证 `maxTurns`；反复请求不存在的工具，验证 `maxUnboundToolCalls` | 记录模型轮数、工具调用数和停止原因；超限后确实结束。CLI 默认 `maxTurns=8`、`maxUnboundToolCalls=3`，演示或调试时可显式覆盖 |
| `reasoning_content` 漏传导致 400 | 用一次最小 API 调用打开 thinking 并带 `tools`；将第一轮 assistant 消息存档，再在下一请求的历史中故意省略该字段 | 留下脱敏后的请求字段、状态码和修复后的成功响应。只在官方当前协议仍要求回传时把 400 作为预期；若协议已变化，记录版本/日期和真实结果，不伪造失败 |
| 后台 asyncio 任务可能被回收 | 创建只等待一个内部 Future 的任务；先让 Future/Task 只通过彼此的等待关系存活，释放外部 Task 引用并在事件循环运行中 `gc.collect()`；再在相同条件下用任务注册表强引用作对照，确认回收后任务仍 pending；最后移除注册表引用并再次回收 | 记录无注册表时的实际警告/存活状态、注册表持有时的 pending 状态，以及释放注册表后的实际结果；正常填入 Future 并完成任务的路径已由 W1 前置实验另行验证。不把“可能”写成必然，也不把程序退出时的取消误判成中途回收 |
| 429 退避与不该重试的错误 | 用 `httpx.MockTransport`（或等价假传输）先返回几次 429 再成功；另跑一次 400；时间等待器可替换为记录调用的假函数 | 证明 429 尝试次数有上限、等待间隔递增且有抖动；400 立即停止；全程不依赖真实限流、不产生额外 API 费用 |
| 上下文压缩是否真的生效 | 配置很小的 token 估算阈值；向 append-only 历史加入一组长对话，再构造下一次请求 | 对照压缩前后的**实际 outgoing messages** 和 token 估算确实下降，同时原始 JSONL 历史记录数/内容不被改写；留下两组计数和样例摘要 |

**单独的事件顺序回归**（不计入五条故障档案）：在 W1 先调用 listener 再更新 state，观察 listener 收到旧 state；恢复正确顺序后两个 listener 都读到新 state。日志作为 W1 证据。
