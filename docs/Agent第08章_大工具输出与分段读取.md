## 1. 先确定任务需要哪些信息

| 任务 | 合适的读取方式 | 需要付出的成本或补充 |
| --- | --- | --- |
| 小文件，需要整体理解 | 在预算内整读 | 少一次定位往返，仍需正确理解内容 |
| 大文件中修改某个功能 | 结构或搜索定位，再读相关行与依赖 | 搜索和展开可能增加调用；关键词可能漏掉间接关系 |
| 全面审查或迁移 | 先建立范围，再系统覆盖，记录未读部分和关联 | 需要较多读取，不能用少数搜索命中替代覆盖 |
| 很长日志中找错误 | 搜索错误、读取附近或末尾 | 必要时向前追溯原因，避免只见最终报错 |

结构概览、关键字命中与摘要都能帮助导航，但都不能证明未展示部分没有相关信息。代码往往还需读取调用方、被调用函数、类型与配置。范围不够时主动扩大读取，跨函数问题按关系补读。全文已经进入模型也不等于推理一定完整。

## 2. 限制单次输出与选择读取范围各有用途

输出上限限制一次结果体积，为超大结果提供明确截断信息与继续取得内容的入口。它不决定下一步必须从头顺序翻页，也不证明更小的片段总能更高效地完成任务。

行范围接口允许直接请求第 180–240 行；搜索返回命中行号后可以跳转到附近。小文件可以整读。最终仍需要单次输出上限与请求总预算，行范围接口本身不能限制一行内的超长内容。

Pi 当前 read 工具的 offset 按行从 1 起算，limit 控制行数，并另行进行行数/字节截断；grep 提供定位信息及上下文选项。教学曾改成字符分页只是为了降低切片难度，缺少实际任务目标，现撤下该练习，不要求先做再重写。

## 3. 多轮与遗漏的取舍

若整个文件最终都需要读，把它切成小片不会自动减少总信息量。如果每段后都调用模型，下一轮又携带已读历史，累计输入和输出还可能增加，并增加等待次数。省下的主要是与当前任务无关的内容，以及避免一次请求超量，不能仅凭单次输出变短就宣称成本下降。

已知互不依赖的几个范围可在一批工具调用中读取，现有只读 gather 规则可复用；搜索结果回来后才能决定位置的步骤仍有依赖。并发可以缩短部分等待，不会自动减少总输入。

按需检索需用更宽上下文、多个线索和依赖关系弥补可能遗漏；全面审阅则记录覆盖范围、保留必要重叠和跨段要点。搜索无结果不能直接证明没有相关实现。

字符数、UTF-8 字节数与 token 数仍需区分。当前 JSON 字符数 //4 只是粗估，请求还包含工具定义，输出也需要预算。具体计量与整段历史组织在后续结合现有请求函数处理。

### 参数 description 与 None 的含义

学员追问参数说明是给谁看，以及模型是否知道 None 代表读到末尾。静态确认两字段已正确命名并保存，read_file 仍返回全文。沿项目调用关系核对：Field(description=...) 进入 model_json_schema()，再由 build_tools_payload 作为 tools 的参数说明发送给模型；开发者也可将它作为文档阅读。工具级 description 描述用途，字段级 description 描述参数用法。

int | None 描述允许的类型；default=None 在缺少 end_line 时由本地参数模型填入值；description 解释这个值的业务含义。None 本身不固有地表示文件末尾，当前“读到哪一行”未说明空值行为，应写明“结束行号，从1开始计数且包含该行；省略或传 null 时读取到文件末尾”。start_line 也写明从1计数、包含该行。

模型通过 JSON 传参数，空值写 null，不写 Python 的 None。json.loads 将 null 转为 None；省略字段则 model_validate 使用默认 None。该值在将来的行列表切片中作为终点时表示取到列表末尾，描述文字不替代实际读取逻辑。当前动作是补清两字段的描述，再继续已布置的正常切片读取路径，不新增验证步骤。

参考：[Pydantic JSON Schema 官方说明](https://pydantic.dev/docs/validation/latest/concepts/json_schema/)。未生成或执行项目 schema 来验证，不将文档例子当作本机运行结果。

## 6. 当前动手：单文件文字搜索

用途是先取得位置再展开正文。例如搜索 a.txt 中的 hello，返回 a.txt:12:hello world，模型可据此请求 read_file 的附近范围。函数按行做大小写敏感的原样子串匹配，输入单个 workspace 相对文件路径；目录递归、复杂索引等按实际需要再展开。

### 参数模型

在 tool_schemas.py 增加 SearchFileArgs，字段为：

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| path | str | workspace 相对文件路径 |
| query | str，min_length=1 | 非空的待查文字，按原样匹配，区分大小写 |
| max_matches | int，default=20，ge=1，le=100 | 最多返回多少个匹配行 |

先解释 min_length 是字符串最少字符数、le 是小于等于，沿用已有 Field 写法。20 是课程可调整默认数量，100 是当前接口允许上限，两者均不是模型窗口限制。

### 搜索函数

在 tools.py 的参数类型导入列表加入 SearchFileArgs，并增加 search_file(file_args: SearchFileArgs) -> str。复用 resolve_workspace_path 检查路径，read_text(encoding="utf-8").splitlines() 得到行列表；本次输出是每个命中行一条记录，因此拆行后不保留原换行符。

enumerate(lines, start=1) 每次提供从1开始的行号和对应行文字；用独立水果列表例子先解释两个变量，再让学员写项目实现。判断 file_args.query in line 表示这行包含待查文字；同一行中多次出现也只返回一条匹配行。

使用列表收集“path:行号:原行文字”，最多收集 max_matches 条。只有在已收满后又发现一条命中时，才停止并追加“仍有匹配未展示，请缩小查询范围或增加 max_matches”的提示；不能仅因数量恰好达到上限就断言还有遗漏。无命中返回明确文字，其余用换行 join 拼成 str。早停时不声称已计算全部命中总数。

这是匹配行数量限制，不是严格结果字节上限；单行极长的情况仍留给后续体积兜底。参数与函数已保存，当前逻辑问题见下文；检查正确后接 tool_specs/tool_arg_models/tool_functions 的注册，不增独立测试脚本，不由教员运行或代写项目代码。

### 最新静态检查：计数与限量的循环范围

SearchFileArgs 的 path/query/max_matches 类型、默认值与约束正确，tools.py 已导入类型并定义函数。工具尚无说明和三处注册，不能报告已接入。函数仍需修正：

- matches 在每次循环末尾增加，实际统计的是扫描行数。建议直接用 len(selected) 表示已保存的匹配行数，省去额外计数和自增。
- 当前先追加命中、后在匹配分支之外检查上限，而且没有 break；超限后仍收集全部命中并反复附提示。应仅在遇到命中时检查是否已收满，检查放在保存当前行之前；已满则说明还有匹配未展示并 break，未满才保存。由此只有额外命中才发提示。
- len(selected)==1 错把唯一匹配当作无结果；无结果应为列表为空。
- splitlines(keepends=True) 保留换行，再用换行 join 会制造多余空行；搜索行记录使用 splitlines()，由最终 join 统一添加换行。
- query 描述写明“按原样匹配，区分大小写”；max_matches 描述说明“最多返回的匹配行数”。“包含大小写”表达不清且放错字段。

用 max_matches=2 的例子解释顺序：第一条命中保存，第二条命中保存，只有遇到第三条命中时追加未展示提示并停止。仅有两条则完整返回，不虚报遗漏。先修正这项现有函数，再注册；本轮不增加验证或故障注入任务。

## 8. 当前动手：统一限制工具结果的 UTF-8 体积

当前按行范围与 max_matches 控制取哪些行，单行仍可能很长。新增最终结果上限，作为进入消息历史前的兜底；模型继续根据任务定位和选择范围，不要求从头顺序翻页，旧字符 offset 作业仍取消。

本次在 agent_runner.py 的 make_tool_result 附近新增内部函数 limit_tool_output(content: str, max_bytes: int = 50 * 1024) -> str，并让 make_tool_result 的 content 字段使用它的返回值。该统一入口也覆盖已有工具错误结果。50*1024 字节是沿用教材量级的初始可调配置，不是 DeepSeek 模型窗口；限制仅指 content 的 UTF-8 字节，不含整个消息 JSON、工具定义或其他历史。

先解释方法：str.encode("utf-8") 返回 bytes，len(bytes) 是字节数；bytes.decode("utf-8") 返回 str。"你好" 有两个 Python 字符、UTF-8 编码六字节。对编码后的正确字节串取开头可能留下半个字符，decode(errors="ignore") 在本用法中丢弃末尾不完整编码，如 "你好" 的前4字节解码保留“你”。不把 ignore 当作所有解码错误的通用处理方式。

由学员实现以下契约，不提供完整函数答案：

1. 输入返回文字，输出仍是 str。准备明确的截断提示，说明结果不完整、仅展示原结果开头，并提示可缩小读取范围或搜索条件后重取。提示可放在正文前或后；位置不作为正确性要求，采用后缀的实现也有效。
2. 用 UTF-8 编码计算结果与提示的字节数。当前唯一调用使用固定默认50 KiB，足够容纳提示；本练习以此有效配置为范围，不要求为人为设置的极小值新增防御分支。将来真实开放配置或作为通用接口时，再确定参数范围和校验。
3. 原结果未超过额度时原样返回，不添加截断提示。
4. 超额时先为提示保留字节额度，其余额度用于原结果的字节前缀，再以 errors="ignore" 解码成文字，与提示拼接。最终连同提示的 UTF-8 字节数不超过 max_bytes。不能按提示的字符数扣预算，也不能先取满额度再额外添加提示。
5. make_tool_result 内调用该函数，为所有原有路径提供最后一道结果体积限制。调用者是程序，函数不登记为模型工具。

原始工具结果可能带完整的行范围说明；截断提示应明确正文仅是该结果的开头片段，不能据原行范围误认为全部正文已展示。执行成功与展示完整性是不同维度。前缀能让接收者先看到不完整说明，后缀也能清楚标明截断；两者均须计入最终字节上限。

本节只增加单条结果体积保护，不是文件流式读取，也不是全请求 token 预算。超长单行在此版仅能展示开头，现有行范围接口不保证恢复该行任意位置，片段搜索等能力以后按真实需求再增加。学员已修正 limit_tool_output：len(encoded) 比较、未超返回原文、按参数扣除提示字节数、UTF-8安全解码均正确，make_tool_result 已接入；当前采用提示前置亦有效。最新静态检查确认唯一调用使用默认50 KiB；学员指出极小额度检查过度防御，教学复核认可。撤销 body_limit < 0 检查的必做要求，按实际使用范围通过，不再要求补两行或另作验证；未声称支持任意非法配置。教员未代改或运行源代码。下一项为请求层读取 API usage。

## 9. 字节上限与 token 预算

单条工具结果用 UTF-8 字节做体积兜底适合当前实现：额度明确、与模型分词方式无关，避免一次返回过多文字。50 KiB 不对应固定 token 数；它只限制该条 content，不能保证整个请求装入上下文。总请求的 token 预算需独立处理，这两层可同时保留。

准确统计不必等到 Agent 更复杂。当前已有按估算触发历史摘要的流程，适合紧接本次体积限制增加 API usage 记录和请求预算；当接近窗口、频繁压缩、需要比较读取/摘要策略的输入开销时，精度的收益更明显。当前 estimate_messages_tokens 将 messages 序列化后按字符数整除4，受文字内容影响，也未计入 tools；只能视为教学阶段的粗估，不能作为严格的窗口保证。

区分三个层次：

- 请求前粗估：便于提前决定是否压缩，但须留误差余量，覆盖系统提示、历史、工具说明和工具结果。
- 请求前本地分词：使用匹配当前模型版本的 tokenizer，能准确计算给定文字；整个聊天请求还须对齐模型实际使用的消息格式、特殊 token 和工具表示。对 json.dumps(messages) 分词得到的是这段 JSON 文本的 token 数，不能据此宣称精确复现服务器输入计数。本地分词通常不需要另调模型。
- 请求后 usage：API 返回的 prompt_tokens/completion_tokens 是已处理请求的实际用量，可观测成本并校准估计；到达时该请求已经发生，不能单独替代请求前的窗口检查。流中断也可能收不到最终 usage。

后续先保留本节字节保护，再记录实际 usage；接着根据当前模型限制建立输入预算，计入 tools，并为输出和估计误差预留空间。需要精确预判时再核对模型兼容的 tokenizer 或供应商计数接口；若供应商未公开完整聊天格式，须明确本地全请求计数仍有误差。DeepSeek 官方提供离线 tokenizer 示例，但本轮未下载、未核对其与当前模型的版本匹配，不能记成已经接入精确计数。

## 10. 当前动手：显示主路径单次请求的实际 token 用量

架构位置为模型请求层 stream_message，仍属第8章请求预算。一次用户任务可能发出多次模型请求，这里显示每次请求的用量，先观察实际消耗，为后续改进粗估与压缩阈值提供依据。

2026-10-20核对DeepSeek官方API：流式响应在[DONE]之前的最后一个JSON数据块携带usage，当前文档不要求为取得最后用量额外设置include_usage；该最后块仍有choices。按当前供应商约定读取，不引入其他供应商的空choices用量块结构。

usage中prompt_tokens表示本次输入、completion_tokens表示本次输出、total_tokens表示两者总量。输入覆盖本次请求的上下文，并非仅本次新用户文字。用独立数据例子说明三个字段：{"prompt_tokens":120,"completion_tokens":20,"total_tokens":140}，对应显示“本次用量：输入120，输出20，合计140 tokens”。这些数是例子，不能写死在项目中。

学员追问“保存”是赋值还是逐字段相加。先明确：usage是服务器已经统计好的字典，三个字段是三项计数，不是三个token，也不是当前文字块的增量。total_tokens已经等于输入与输出之和，不把三项再相加。此处保存指在本次stream_message的局部变量中保留整份字典，便于循环结束后读取显示；跨请求累计才另设计数器、每次请求加一次，当前不做累计。

对应赋值关系用局部片段说明：先前用chunk_usage临时变量并判断非None再保存，作用是保留最后一次有效统计、不被后续空值覆盖。当前DeepSeek文档规定usage位于最后JSON块，随后就是[DONE]，因此可直接在chunk=json.loads(data)后写usage=chunk.get("usage")，中间变量不是必需，不作为通过要求。结束后读取usage["prompt_tokens"]等字段用于print，按单次请求显示一次。

循环外usage=None只是给尚未赋值的路径一个初始状态：Python的for/async for没有独立块作用域，循环内赋值之后循环外可以读取，不需要预先声明。若赋值语句一次都没执行，后续直接读取变量才有未赋值的问题；已有控制流能保证赋值时也可省略初值。建议初值一行加循环内直接赋值，便于表示未知，但不为这一写法另设过关门槛。学员采用其他保证读取前已赋值的简单写法也接受。

由学员在agent_runner.py的stream_message中实现：

1. 推荐在读取流之前初始化usage=None，表示尚未收到统计；若控制流已保证后续读取前一定赋值，可省略，不作为强制格式。
2. chunk=json.loads(data)后、现有delta解析之前，直接usage=chunk.get("usage")即可。当前最后JSON块带统计，[DONE]在解析前break，不会再覆盖该值；保持已有正文和工具调用处理。
