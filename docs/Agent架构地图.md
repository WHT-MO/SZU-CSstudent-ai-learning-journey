# Agent v1 架构地图

## 一句话定义

Agent = **模型 + 会话状态 + 工具注册表 + 工具执行器 + 循环控制**。

模型负责判断下一步要回答还是要调用工具；程序负责校验、执行工具，并把结果交回模型。

## 最小数据流

```text
用户问题
  ↓
messages（会话状态）
  ↓
请求模型（当前主路径走流式）
  ↓
模型响应
  ├─ 无 tool_calls：保存回答并结束
  └─ tool_calls：模型需要工具
        ↓
      读取工具名和 arguments
        ↓
      Tool Registry（工具注册表）查找工具
        ↓
      Pydantic 参数模型校验
        ↓
      执行真实工具
        ↓
      生成 role=tool 的结果消息
        ↓
      追加回 messages，再次请求模型
```

## 五个模块

### 1. 会话状态 `messages`

保存用户消息、模型消息和工具结果。模型每次只能根据传入的消息理解上下文。

### 2. 模型请求

程序把 `model`、`messages`、工具说明和请求选项发送给 API。当前主路径用 `stream_message()` 逐行读取 SSE（服务器推送事件），分别累加正文、`reasoning_content` 和工具调用分片，返回含message、completed、reason的字典。模型层返回结构及调用方读取已静态通过，原因包括原有请求失败及响应不完整。非流式函数名为 `non_stream_message()`，当前作为备用实现；主循环的实际调用是流式函数。

当前请求前通过 `prepare_request_messages()` 构造请求视图，超预算时更新旧历史摘要，保留当前轮原文；摘要失败时按既有策略保留当前轮。原始会话仍由 `messages` 保存，摘要缓存及覆盖位置已持久化。请求、解析和摘要生成已归入独立的 `model_client.py`，迁移整体静态通过，边界见[进阶第3节](Agent进阶03_模型调用模块.md)。

### 3. 工具注册表

根据工具名找到对应的参数模型和执行函数。实际资料在 `tool_registry.py` 集中登记并生成查找结构，下面仅展示其中部分参数类映射的形状：

```python
tool_arg_models = {
    "read_file": ReadFileArgs,
    "write_file": WriteFileArgs,
    "list_files": ListFilesArgs,
    "edit_file": EditFileArgs,
}
```

### 4. 参数校验与工具执行

模型返回的 `arguments` 先从 JSON 字符串转换成 Python 字典，再用参数模型校验。校验通过后，才执行真实文件操作。

工具说明书告诉模型“怎么调用”；执行函数才真正读写文件。两者不是同一件事。

### 5. Agent Loop

循环不是“不断运行代码”这么简单，它表示：

```text
模型要工具 → 执行工具并回传结果 → 再问模型
模型给最终回答 → break
```

必须有停止条件，例如无工具调用、最大工具调用轮数或请求失败。正文和工具调用可以同时出现，完整响应后的主分支根据是否有 `tool_calls` 判断下一步。

## 本节对照：三个函数

- `stream_message()`：请求和解析一次模型回复，返回含消息、完整性与原因的结果字典。
- `execute_validated_tool()`：执行一个已校验的工具，返回 tool 结果消息。
- `run_agent()`：组织消息和调用顺序，把模型消息和工具结果加入历史后再次请求模型，最后返回包含message、completed、reason的任务结果；其中completed表示取得完整最终回答。

具体讲义见 [职责与调用关系](Agent第02章_职责与调用关系.md)。
