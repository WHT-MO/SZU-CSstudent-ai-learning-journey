## 1. 这一节结束应当能做什么

重新启动 Agent 后，恢复完整 messages、已有摘要和摘要覆盖位置，继续通过 build_request_messages 构造下一次请求。

当前源码中，load_messages 只恢复完整历史；run_agent 又创建 summary 为 None 的新缓存。因此旧摘要不会跨任务保存，即使原始对话一直还在 session.json 中。

教材区分两个问题：数据存在哪里，以及会话在逻辑上如何组织。Pi 的 coding-agent 使用 JSONL 文件和会话树，并由 buildSessionContext 构造模型需要的线性消息列表；压缩记录携带摘要和保留边界。

## 3. 应当保存的数据

把 session.json 最外层从消息列表改为一个字典，包含两个字段。序列化之前的 Python 数据形态为：

```python
{
    "messages": messages,
    "summary_cache": summary_cache,
}
```

| 数据 | 含义 |
| --- | --- |
| messages | 完整原始历史，保留已有 system、user、assistant 和 tool 消息 |
| summary_cache["summary"] | 最近一次成功生成的摘要；没有时为 None |
| summary_cache["next_message_index"] | 原始 messages 中第一条尚未被摘要覆盖的消息下标 |

两部分一起写进同一个文件，沿用临时文件写入后替换的原子写入方式。这样一个文件版本中的摘要边界始终对应该版本的原始历史。

request_messages 每次由 build_request_messages 重新构造。磁盘保留完整 messages，后续仍能回看摘要所依据的原文。

例如：摘要已经覆盖 A、B，完整历史随后还有 C。重启后恢复摘要及 C 的起点，再追加新任务 D，请求视图就是 system + 摘要(A、B) + C + D。覆盖位置用原始历史的下标。

## 5. 保存时机为什么要补两处

当前第一次保存发生在用户消息追加之后，准备请求之前。这次写入还没有包含本次准备函数可能生成的新摘要。

例如：先保存历史 → prepare 更新了摘要 → 模型请求失败并返回 None。若仅沿用原有保存点，新摘要没有写盘。下一次启动仍会加载旧缓存。

在两处 prepare 返回后保存，可以使刚生成的摘要与覆盖位置及时写盘。其他已有保存点继续负责保存新增回答和工具结果。

## 10. 继续：存储格式与会话结构

教材把存储介质与逻辑结构分开讨论。对应本项目可以再分清文件编码方式：

| 层面 | 当前实现 | 教材Pi示例 |
| --- | --- | --- |
| 存储介质 | 本地文件 | 本地文件 |
| 文件格式 | 整份JSON，保存时重写 | JSONL，每行一条记录，便于追加 |
| 逻辑结构 | 线性历史 | 带父节点关系的会话树 |
| 模型入口 | build_request_messages生成线性消息 | 从当前路径构造线性消息 |

JSONL本身不会产生分支。会话树为记录分配id、用parentId指向前一节点，并用leafId表示当前继续的位置；从同一节点接出不同记录即可保留两条尝试。构造请求时沿当前节点的父关系回溯、反转，只选当前路径，再应用该路径上的摘要。

当前线性历史满足已有功能。会话树的实际实现随回退、重试分支或保留多条尝试的需求安排，不为对齐教材结构强制重写现有会话存储。上述原理讲解不等同独立实现证据。
