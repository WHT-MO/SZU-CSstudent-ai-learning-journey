# Agent 第 6 章：消息的三种用途

> 2026-10-20，现有 Python 项目对照讲义。与第 5 章剩余说明合并讲解；提供讲解不等于已取得学员独立复述或实现证据。

## 1. 同一次运行中，三种用途不同

| 数据或输出 | 用途 | 当前入口 |
| --- | --- | --- |
| messages | 保存完整对话与工具往来，供恢复会话 | load_messages / save_messages |
| request_messages | 提交给本次模型请求，可能经过摘要或裁剪 | prepare_request_messages |
| 终端显示 | 让用户看到正文、进度和错误 | print / 流式输出 |

这是用途区分，不表示必须复制三份数据。目前预算内 prepare_request_messages 可以直接返回同一个列表；摘要或裁剪时，请求内容才与完整历史不同。终端打印也不会自动写入历史。

## 2. 一次工具往返怎样留下记录

以读取笔记为例，记录顺序为：用户提出要求 → assistant 给出工具调用 → tool 返回内容 → assistant 根据内容回答。

assistant 的 tool_calls 表达模型要求程序执行什么；工具函数运行完成后，程序创建 role=tool 的结果。结果的 tool_call_id 与调用的 id 对应，解决同一批多个调用的配对。模型不会直接运行本机 Python 函数。

当前 run_agent 先加载历史，加入用户消息并保存；取得完整工具调用、执行和回填后，把 assistant 调用消息与整批 tool 结果一起加入历史并保存，再准备下一次模型请求。普通完整回答也加入历史并保存。这里的历史排列与代码实际追加时刻要区分，当前不是边执行单个工具边持久化单条结果。

## 3. 已显示、已保存、可以执行是不同条件

现有策略保留不完整的普通文字，增加中文中断提示；不完整的工具调用不会执行。看到一段输出不代表已有可执行的完整参数，也不代表该输出已自动保存。

这些是当前项目已选择的行为，不为本节增加新状态字段或更换中文提示。以后自动重试等程序需求需要识别中断时，再设计相应结构。

## 4. 工具通知放在哪里

“准备执行工具 call_1”用于界面显示运行进度；“call_1 读取到 hello”才是工具执行结果。开始通知通过程序事件交给显示函数，不作为 role=tool 消息追加到模型对话。
